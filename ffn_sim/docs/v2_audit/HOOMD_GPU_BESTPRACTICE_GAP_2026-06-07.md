## 1. Executive summary

The core finding: **our production single-cell GPU path is host-bound by construction, and that is the entire gap.** HOOMD's foundational design idiom is full device-residency — particle data lives in GPU memory, *all* simulation work (forces, integrators, neighbor search, MPI) runs on the GPU, and the CPU "merely acts as a driver" (Glaser et al. 2015, CPC 192:97, verbatim). We invert this in the frozen production path.

- **Per-step host sync is the headline gap.** The FROZEN production integrator `LeimkuhlerMatthewsBAOAB` (`ffn_sim/integrator/baoab.py:180`) is a Python `hoomd.custom.Action` that opens `sim.state.cpu_local_snapshot` **every step** (`baoab.py:408`). On a GPU device the HOOMD docs grade `cpu_local_snapshot` as zero-copy *only* guaranteed on CPU ("access may be zero-copy if running on GPU" — i.e. it may copy), so this forces a device→host→device round-trip per timestep — exactly the "data copied back and forth" anti-pattern the 2015 paper names as why a code fails to exploit the GPU.
- **`methods=[]` by contract.** Our `md.Integrator` carries forces but no built-in integration method (`cortex/cortex.py:973`, `cell/cell.py:785`); HOOMD's GPU-resident `md.methods.*` time-stepping is deliberately bypassed and replaced by the Python Action. This is a *justified science choice* (the Leimkuhler-Matthews BAOAB-limit two-Gaussian step is not a HOOMD built-in; `md.methods.Brownian` is O(δt) Euler-Maruyama, `OverdampedViscous` is noiseless), **not an oversight** — but it is the structural reason we own the GPU-perf burden HOOMD normally handles in C++.
- **Binder updaters use HOOMD's heaviest API.** The myosin/xlink/integrin updaters call the *global* `get_snapshot()` / `set_snapshot()` (docs: O(N_particles + N_bonds + …), "very expensive when the simulation device is a GPU") every batch — `cortex/myosin.py:999/1446`, `cortex/crosslinkers.py:950/1172`, `bridge/integrin_bonds.py:235/365` — to mutate a handful of bonds.
- **Host scipy cKDTree duplicates the on-device nlist.** Myosin/xlink rebuild a `scipy.spatial.cKDTree` on the host every batch (`myosin.py:1104/1198`, `crosslinkers.py:1060`) — an O(N log N) host recomputation of a spatial-neighbor structure HOOMD already maintains on the GPU (`md.nlist.Tree`, attached at `crosslinkers.py:1426` for the LJ force, queryable from Python via `pair_list`/`gpu_local_nlist_arrays`).
- **97%-util / ~64 W signature = launch/occupancy-bound, NOT FLOP-bound.** Native 38k-filament / 266k-particle runs on the A5000 sit at 97% GPU util but only ~64 W of an 80–165 W TDP, ~25 steps/s, VRAM 1.95/16 GB (12%). This is the textbook many-small-kernel-launch signature: the constrained solver issues ~38k tiny per-chain 6×6 ops as many small per-step cupy kernel launches (`constrained_baoab.py` Fixman/Thomas/SHAKE loops at `:545/:551/:555/:313/:319/:404`).
- **Double precision build.** Our install is `floating_point_precision = (64, 32)` — FP64-high / FP32-reduced — confirmed live. HOOMD's flagship single-GPU benchmarks are largely FP32; FP32 is real and available but is a from-source rebuild (`HOOMD_LONGREAL_SIZE=32`), and our SHAKE/Fixman drift tolerance (1e-9…1e-10) sits at the FP32 boundary, so precision is a *low-priority, risky* lever for us — not the wrong-sized lever a generic LJ run would have.
- **Autotuner never invoked.** Zero `tune_kernel_parameters` / `is_tuning_complete` / `kernel_parameters` call-sites in the codebase (confirmed). HOOMD requires thousands–tens-of-thousands of steps for its own kernels (LJ/nlist/bond) to lock optimal launch params; our reported ~25 steps/s may be partly on un-tuned HOOMD kernels. (Caveat: this only helps HOOMD's *own* kernels, not our hand-written cupy kernels.)
- **We already wrote the correct idiom — it is gated off.** `OverdampedBAOABDevice` (`baoab_device.py:250`, single fused `cupy.RawKernel`) and `ConstrainedLeimkuhlerMatthewsBAOAB` (`constrained_baoab.py:622`, `gpu_local_snapshot` + cupy `xp` dispatch) prove the device-resident port is feasible and *done* for two of three variants. The frozen `baoab.py` is the un-ported laggard; the constrained Action is device-resident but **not fused** (still launch-bound).
- **What idiomatic HOOMD does instead:** keep the entire `Simulation.run(N)` loop in compiled C++/CUDA on-device, re-enter Python only when a `Trigger` fires, read/write via `gpu_local_snapshot` (cupy, copy=False) not the global snapshot, reuse the on-device nlist for candidate search, and let the built-in autotuner lock kernel launch params.
- **Single highest-impact lever:** eliminate the per-step host round-trip on the production single-cell path — i.e. promote + validate the already-written device-resident BAOAB Actions so the integration loop stays on the GPU. This is the largest single closeable divergence; it is PI-gated because `baoab.py` is integrator-frozen.

## 3. Reference architecture — how fast HOOMD / GPU-MD code is structured (the "should-be")

**Principle 1 — full device-residency.** HOOMD's defining design choice is that particle data structures live in GPU memory and *all* simulation work runs on the GPU; the CPU is a driver. Glaser et al. 2015 (Comput. Phys. Commun. 192:97, DOI 10.1016/j.cpc.2015.02.028) state it verbatim: *"It uses completely device-resident data structures, all simulation work is performed on the GPU so that the CPU merely acts as a driver for the GPU,"* and name the failure mode directly: codes "do not take maximum advantage of the GPU if the particle data structures are not GPU-optimized and data needs to be copied back and forth between the CPU and the GPU." The same paper: *"The single-GPU version of HOOMD-blue does not transfer any significant data between the host and the device during simulation."*

**Principle 2 — every step on the GPU, including the integrator.** The original 2008 paper (Anderson, Lorenz, Travesset, J. Comput. Phys. 227:5342, DOI 10.1016/j.jcp.2008.01.047) established this precisely because the mixed CPU/GPU "gather on GPU, integrate on CPU" approach caps speedup at "a factor of 2 or 3 at most" — it was "the first implementation of a general purpose MD code where all steps of the algorithm are running on the GPU." On integration: "It is important … that this step is done on the GPU, even if … the computation takes very little time on the CPU. When done on the CPU, forces calculated on the GPU [must be copied back each] time step." The 2020 v3-design paper (Anderson, Glaser, Glotzer, Comput. Mater. Sci. 173:109363, DOI 10.1016/j.commatsci.2019.109363) restates it: *"With very few exceptions, all of the time-consuming operations … can execute on the GPU, including all of the data structures, force evaluations, integrators, and MPI communication."*

**Principle 3 — built-in compiled, device-selected integration methods.** HOOMD ships GPU-resident integration methods as compiled C++/CUDA `TwoStep` class pairs selected by device at attach. Confirmed present in the live 7.0.1 install: `md.methods.Brownian`, `Langevin`, `ConstantVolume` (NVE/NVT), `ConstantPressure` (NPT), `OverdampedViscous`, `DisplacementCapped`, plus the `md.methods.rattle` family (manifold-constrained `Brownian`/`Langevin`/`NVE`/`OverdampedViscous` + `Manifold`/`MethodRATTLE`). Docs: `Langevin` "integrates particles forward in time according to the Langevin equations of motion, modelling a canonical ensemble (NVT)." The idiom is to attach one of these as the `md.Integrator` method and let `Simulation.run()` drive the whole step on-device.

**Principle 4 — the `Simulation.run(N)` batch model.** One Python `run(N)` call advances N timesteps with the per-step schedule (tuners → updaters → integrator → writers) executed inside the C++/CUDA loop; Python is re-entered only for operations whose `Trigger` fires (e.g. a `Periodic(100)` writer fires on steps 100, 200, …). The idiom is **few Python touches per many steps**.

**Principle 5 — the snapshot cost hierarchy.** HOOMD's `State` docs grade the three host↔device access APIs (verbatim, latest/7.0.1):
- `gpu_local_snapshot` — "provides zero-copy access on the GPU (assuming data was last accessed on the GPU)."
- `cpu_local_snapshot` — "zero-copy is guaranteed on CPU, access may be zero-copy if running on GPU" (i.e. *not* guaranteed; may copy on a GPU run).
- `get_snapshot` / `set_snapshot` — "order O(N_particles + N_bonds + …)"; `set_snapshot` is "very expensive when the simulation device is a GPU."

The device-resident idiom for a custom Action is to wrap the GPU buffer with cupy via `cupy.array(data.particles.position, copy=False)` inside `gpu_local_snapshot` — no host round-trip. The `gpu_local_snapshot` arrays expose `__cuda_array_interface__` (v2), so cupy/Numba/PyTorch can consume them directly.

**Principle 6 — autotuned kernel launch params.** HOOMD's GPU kernels are `AutotunedObject`s: `tune_kernel_parameters()` "will vary the kernel parameters in subsequent time steps, check the run time of each, and lock to the fastest performing parameters after the scan is complete"; `is_tuning_complete` is True "when tuning is complete and kernel_parameters has locked optimal parameters for all active kernels." "Typical operations require thousands of time steps to complete tuning. Some may take tens of thousands or more." Idiomatic timing gates on `is_tuning_complete` + a warm cache; Glaser 2015 discards a 20,000-step autotuner warm-up before timing.

**Principle 7 — on-device neighbor search, reused.** `md.nlist.Cell` / `Tree` (LBVH) / `Stencil` are maintained on the GPU with an `r_buff` skin (a list built one step is reused until a particle moves `buffer/2`). The nlist is queryable from Python — confirmed live: `NeighborList.pair_list`, `local_pair_list`, `cpu_local_nlist_arrays`, `gpu_local_nlist_arrays` (read-only), plus `num_builds` / `shortest_rebuild` diagnostics — so reactive/dynamic-bonding logic can read the candidate pairs HOOMD *already* computed on-device instead of recomputing a host KDTree. (Cross-engine precedent: LAMMPS `fix bond/create` finds reaction candidates by reusing the existing non-bonded neighbor list, not a separate KDTree.)

**Principle 8 — compiled-component escalation.** When the Python custom-Action path is the bottleneck, HOOMD's documented path is to compile a C++/CUDA external component: latest `components.html` — "Extend HOOMD-blue with a component implemented in C++ for performance-critical tasks, such as pair potential evaluation." This is how the built-in methods themselves exist; a custom `IntegrationMethodTwoStep` subclass can be added to `md.Integrator.methods` and reuse HOOMD's autotuner + on-device RNG + box-wrap.

**Principle 9 — precision is a build-time choice.** `HOOMD_LONGREAL_SIZE` (default 64) and `HOOMD_SHORTREAL_SIZE` (default 32): at 64, "particle coordinates, sum quantities, and … integration are performed in double precision"; at 32, single. Our conda-forge 7.0.1 build is `(64, 32)` (confirmed live) — FP64 integration. FP32 is a from-source rebuild.

**Principle 10 — multi-GPU is for already-saturated single GPUs.** Glaser 2015's headline is MPI domain decomposition strong-scaling to thousands of GPUs / 10⁸ particles — the right lever when one GPU is FLOP-saturated, *wrong* when launch/occupancy-bound at 12% VRAM on one GPU.

## 6. Deep-dive: the per-step host-sync anti-pattern

This is the single highest-leverage divergence. The frozen `LeimkuhlerMatthewsBAOAB.act()` enters `with sim.state.cpu_local_snapshot as snap:` on **every** integration step (`baoab.py:408`). On a GPU device, the HOOMD `State` docs grade `cpu_local_snapshot` as zero-copy "guaranteed on CPU, access *may be* zero-copy if running on GPU" — the "may be" is load-bearing: a CPU snapshot on a GPU run is not guaranteed to avoid a copy, and reading `.position`/`.net_force` as host numpy forces the device buffers to the host. The act then does host RNG (`np.random.standard_normal`, `baoab.py:466`) and a host box-wrap (`baoab.py:487`) and writes back — a full device→host→device round-trip per step.

Why this caps us at host speed regardless of the GPU: the per-step host sync serializes the GPU pipeline (the GPU cannot run ahead of the host that gates every step), and Glaser 2015 states the single-GPU code "does not transfer any significant data between the host and the device during simulation" — we do the opposite. The downstream Amdahl consequence is documented in our own audit (`GPU_MAIN_PORT_2026-05-31.md`): the per-step sync throttles HOOMD's own ~71%-C++ force eval, making the ~22% Python solver the new bottleneck. The ~13-min host-bound native warm-up is this path running.

The correct idiom is `gpu_local_snapshot` ("zero-copy access on the GPU") + cupy `copy=False`, which is exactly what our *own* ported Actions do (`constrained_baoab.py:837-838`, `baoab_device.py:428-429`) — so the gap is porting debt on a frozen file, not a HOOMD limitation. **Note:** the precise *byte cost* of the per-step copy is a general-GPU-MD principle plus the docs' "may be zero-copy" wording — the HOOMD docs do not contain a verbatim sentence stating "cpu_local_snapshot on a GPU forces a per-step host copy." Our own `baoab_device.py` comment ("that sync is poison for the per-step production GPU path") corroborates by design intent. Treat as verified-by-principle, not verified-by-doc-quote.

## 7. Deep-dive: integrator — Python `custom.Action` vs compiled IntegrationMethod / plugin

HOOMD's GPU integration methods are compiled `TwoStep` C++/CUDA class pairs, device-selected at attach (the Python `methods.Langevin._attach_hook` picks `_md.TwoStepLangevin` on CPU vs `_md.TwoStepLangevinGPU` on GPU). The reference GPU kernel (`TwoStepBDGPU.cu`) does one thread per particle: `position += (net_force + random_force)*dt/gamma` fully on-device, counter-based on-device RNG seeded by `Seed(RNGIdentifier, timestep, seed)`, `box.wrap` on the GPU, `d_pos[idx]` write-back — no CPU transfer, no snapshot copy. These kernels are wrapped in an `Autotuner` that scans block size and locks the fastest. **This is structurally identical to our `baoab_device.py` fused RawKernel** — confirming our GPU-port direction is correct; the gap is that this kernel, not the `cpu_local_snapshot` Action, is the default.

Why we cannot just reuse a built-in: our integrator is the Leimkuhler-Matthews BAOAB-limit, which averages two Gaussians (Wₙ + Wₙ₋₁) to reach O(δt²) on stiff/harmonic systems. HOOMD's `md.methods.Brownian` is overdamped Euler-Maruyama with a *single* uniform random force per step (O(δt), the D3-forbidden option), and `OverdampedViscous` is deterministic (`r += (F/γ)dt`, no noise, O(δt)) — both verified unsuitable. A `md.force.Custom` can add the conservative force but cannot inject the two-step Gaussian-averaged noise. So the only HOOMD-native performant route is a **compiled custom `IntegrationMethodTwoStep`** (external component, `.cc`+`.cu`) added to `md.Integrator.methods` — mirroring `TwoStepBDGPU`. The documented external-component mechanism exists ("Extend HOOMD-blue with a component implemented in C++ for performance-critical tasks").

Cross-engine precedent for the compiled route for *this exact* scheme: LAMMPS `fix gjf` (Grønbech-Jensen/Farago) implements the same two-random-force-average ("the average of two random forces representing half-contributions from the previous and current time intervals") as a compiled in-core integrator with a GPU-suffix route; OpenMM `CustomIntegrator` JIT-compiles the integrator expression to a GPU kernel (Lepton `CompiledExpression`), and `openmmtools` ships `BAOABIntegrator`/`GeodesicBAOABIntegrator` built on it. **No mature GPU-MD engine runs this class of integrator as a per-step host Python loop with a snapshot copy** — our frozen Action is the outlier; our `baoab_device.py` is the idiom we already wrote.

The constrained variant has a template too: HOOMD ships GPU-compiled `TwoStepRATTLE{BD,Langevin,NVE}GPU` that do the constraint projection inside the GPU kernel. **Caveat (verified):** `md.methods.rattle` is *manifold/geometric*-constraint RATTLE (live install shows `Manifold`/`MethodRATTLE`), **not** holonomic pairwise-bond SHAKE — it is a structural template, not a drop-in for our rigid-bond chains + Fixman pseudo-force.

## 8. Deep-dive: dynamic binding/reactions — scipy cKDTree on host vs reusing HOOMD's on-device nlist

The myosin and xlink binders rebuild a fresh `scipy.spatial.cKDTree` over all cortex actin on the host every batch (`myosin.py:1104` segment-projection, `:1198` legacy; `crosslinkers.py:1060`), then `query_ball_point`. Meanwhile `crosslinkers.py:1426` already instantiates `md.nlist.Tree(buffer=0.5*lj_sigma)` on-device over the *same* `actin_cortex` particles for the LJ excluded-volume force. So a queryable on-device neighbor structure exists and is simply not consulted — a pure O(N log N) host recomputation of information already on the GPU, plus the global `get_snapshot()` host pull that feeds it.

The idiomatic substitute is verified-present in our 7.0.1 install: `NeighborList.pair_list` (global, particle tags, rank-0), `local_pair_list` (rank-local indices), and `cpu_local_nlist_arrays` / `gpu_local_nlist_arrays` (read-only). The candidate pairs HOOMD computed on-device can be read back instead of recomputing a tree — exactly how LAMMPS `fix bond/create` finds reaction candidates (reuse the non-bonded nlist, not a separate KDTree).

A critical correctness boundary tempers the fix: **local snapshots (CPU or GPU) cannot resize the system** — you cannot add/remove bonds or particles, or change the box, inside a local-snapshot context (docs: "changing the global or local box within a LocalSnapshot context manager is not allowed"). Our own `integrin_bonds.py:227-230` notes this. So the *count-changing* bond delta legitimately requires a global `Snapshot` + `set_snapshot()` (which rebuilds the nlist). What does **not** need the global snapshot is (a) the per-batch position READ (a `gpu_local_snapshot` cupy `copy=False` read suffices) and (b) the Bell-Evans/Pereverzev `k_off` + break-probability math (embarrassingly parallel, the "EASY: cupy elementwise" roadmap item). The avoidable cost is the full particle-block copy and the host tree; the unavoidable minimum is the bond-count delta.

Cross-engine reality check (verified): LAMMPS does **not** GPU-accelerate its reactive fixes — a GPU build raises "Unknown fix style" for `fix bond/create`. This independently validates two of our conclusions: (a) the right candidate-search structure is the engine's already-maintained nlist, reused; and (b) keeping topology-mutation bookkeeping host-side (with only the candidate query + force eval on-device) is *normal even in a mature, heavily-optimized engine* — full device-resident reactive topology is genuinely hard, not merely something we fail to do.

## 9. Deep-dive: the 97%-util-64W launch/occupancy-bound signature

97% GPU util but only ~64 W of an 80–165 W TDP is the textbook launch/occupancy/dispatch-bound diagnosis, not FLOP-bound: "util" means a kernel is almost always resident; low power means each resident kernel is tiny/low-occupancy, so SMs are mostly idle within the kernel and most wall-time is kernel-launch + Python-dispatch latency. VRAM at 12% confirms it is not bandwidth/capacity-bound — at 266k particles a single GPU has huge unused headroom (HOOMD's own device howto: by 131,072 particles "the GPU is always both faster and more efficient than the CPU," and GPU TPS only halves when system size grows 64×).

Three contributors, with different fixes:
1. **Our own un-tuned cupy kernels.** The constrained solver's batched Thomas m-loop, Fixman G-build loop, and SHAKE Newton iterations launch ~38k tiny per-chain 6×6 ops as many small per-step cupy kernels (`constrained_baoab.py:545/551/555/313/319/404`). These use a fixed/default block size and are **outside HOOMD's autotuner entirely** (it only tunes HOOMD's own compiled kernels). The fix is *our* kernel fusion / compiled CUDA plugin (roadmap lever #3) — fewer, larger kernels raise occupancy and drive power toward TDP. `baoab_device.py` already proves the fused-single-kernel fix for the simple case; the constrained case has not received it.
2. **HOOMD's own kernels, never autotuned.** Zero autotuner call-sites means HOOMD's LJ/nlist/bond kernels (the ~71% C++) may be running on un-locked launch params, and our ~25 steps/s is partly un-tuned. The fix is measurement hygiene: drive `tune_kernel_parameters()` to `is_tuning_complete` before timing, then report. This is free and zero-risk but helps *only* HOOMD's kernels, not our cupy hotspots.
3. **Per-sample host drain.** The host O(N) method-of-planes reduction + GSD writes between `sim.run()` calls drain the GPU to ~0% then refill to 97% each sample. The fix is on-device cupy reduction + lower write frequency (lever #5).

The causal claim "fuse small kernels → raise occupancy → power toward TDP → launch-bound becomes compute-bound" is general GPU-occupancy theory, not a verbatim HOOMD-doc statement.
